La consulta EAS exige FINISHED, plataforma, proyecto, package, perfil, commit, versión y mensaje exactos. El token sólo existe en el paso build:view. La descarga acepta HTTPS y debe coincidir con la huella congelada; URLs firmadas y respuestas crudas permanecen temporales.

Debug debe ser depurable; production no. El manifiesto Debug declara usesCleartextTraffic=true, pero su minSdk24 y NSC explícita hacen que la política de tráfico resida en la NSC. Se comprueba desde el recurso compilado: base/API sin HTTP, trust system y dos pines; sólo los cuatro hosts de desarrollo previstos admiten HTTP. Release exige además el flag false y ninguna excepción Metro. La precedencia de la NSC está [documentada por Android](https://developer.android.com/guide/topics/manifest/application-element#usesCleartextTraffic).

SYSTEM_ALERT_WINDOW pertenece al manifiesto debug de React Native; CHANGE_WIFI_MULTICAST_STATE pertenece al launcher debug de Expo. Se registran como permisos exclusivos de desarrollo y se rechazan en release; no se describen como funciones de Sport Center.

Command-line Tools23 y sus dos JAR fijados decodifican manifiesto y NSC. Build Tools37 verifica firma y alineación. Bundletool1.18.3 se verifica por SHA256 contra su release oficial. El AAB se valida con bundletool y jarsigner antes de generar un APK universal con una llave temporal exclusiva de la prueba. Se conserva la relación AAB SHA256 → APK derivado SHA256 y su certificado de prueba; esa firma no es la identidad de Play App Signing.

En API34 x86_64, Debug usa la AVD nueva profiles-debug34 y release usa otra AVD nueva profiles-release34. No comparten estado Android ni instalación entre perfiles. Cada invocación acepta sólo debug34, release34 o api36; el modo mixto api34 se rechaza. En Debug se inicia Metro en loopback con adb reverse. El proceso Node de Metro usa `--dns-result-order=ipv4first`: la reproducción con SDK57 mostró que localhost puede enlazar sólo IPv6 aunque el CLI anuncie 127.0.0.1. Esta opción alinea el bind con la URL anunciada, el sondeo de disponibilidad y el reverse; no modifica NODE_OPTIONS global, la app ni su política de red. La URL del servidor se obtiene de `/_expo/open?platform=android&runtime=custom` y del manifiesto Android real; se exige exactamente `http://127.0.0.1:8081`, sin credenciales, y se contrastan app, proyecto y SDK57 cuando esos datos están presentes. Cada recorrido limpia el estado, espera Development Build, introduce esa URL en el campo HTTP y pulsa Connect, mediante la UI existente en SDK57. A continuación exige el texto completo de bienvenida del Developer Menu y su botón Continue, conserva una captura y pulsa ese botón. Continue termina el onboarding pero mantiene el menú normal abierto: se exige Reload visible, se pulsa Back una sola vez y se exige que el menú desaparezca. Después siguen siendo obligatorias las aserciones de inicio, catálogo y detalle. Ninguna de estas acciones es opcional ni sirve como fallback. Se registra `launchMethod=launcher-url-input`; este procedimiento no acredita el deeplink que falló en la revisión anterior ni usa un fallback oculto. Al terminar se detienen únicamente los procesos propios, se retira el reverse y se desinstala Debug. Release sólo se instala en su AVD nueva después de comprobar cleanup Debug de esta misma automatización y que Metro, reverse y el paquete anterior están ausentes. Un fallo Debug permite comprobar release si la limpieza fue aprobada; cada fase se registra una sola vez. El agregado API34 se calcula con ambos resultados: queda incompleto mientras falta una fase y permanece fallido si cualquiera falla, aunque la otra apruebe. Si falla la limpieza se aborta inmediatamente. Todos los comandos Maestro llevan `--device` y el serial comprobado por ADB antes de `test`, sin depender de ANDROID_SERIAL.

En una AVD nueva API36 x86_64 google_apis_ps16k se exige una página real de 16384 bytes antes y después, se desactiva la compatibilidad de 4 KB y se ejecuta el derivado release. Es una simulación oficial x86_64; no acredita ejecución ARM64 nativa. Esta AVD nueva puede comprobarse tras un fallo API34 únicamente si inspección y KVM aprobaron y la ejecución no está cancelada. No convierte el fallo API34 en aprobado. Cada fase registra resultados separados, proceso y crash buffer acotado. Un fallo o una omisión requerida bloquea el agregado.

La evidencia conserva sólo JSON, JUnit y capturas públicas durante 14 días. No conserva APK/AAB/APKs, claves, contraseñas, URLs firmadas, tráfico, logcat o logs crudos. La prueba física aplazada, las rutas privadas, los pagos y la revisión de Google Play quedan fuera de esta comprobación.

La apertura por URL escrita corresponde a `ServerUrlInput.connectToURL → HomeAction.OpenApp → DevLauncherController.loadApp` en expo-dev-launcher57.0.21. La selección explícita corresponde a [Maestro2.12 App.kt](https://github.com/mobile-dev-inc/Maestro/blob/0df4cf3c8cad946e0494f462c6ce4987145cd36f/maestro-cli/src/main/java/maestro/cli/App.kt#L97-L101) y [TestCommand.kt](https://github.com/mobile-dev-inc/Maestro/blob/0df4cf3c8cad946e0494f462c6ce4987145cd36f/maestro-cli/src/main/java/maestro/cli/command/TestCommand.kt#L612-L621); un serial explícito desconectado no autoriza escoger otro dispositivo.

El onboarding corresponde a `expo-dev-menu57.0.20`: `Onboarding.kt` define el texto y Continue; `DevMenuAction.FinishOnboarding` no cierra el menú. Su preferencia privada `isOnboardingFinished` parte de false y cada `clearState` de Maestro vuelve a borrarla mediante `pm clear`, por lo que se comprueba en ambos casos. El cierre por Back corresponde a `BottomSheetScaffold → ModalBottomSheet` de [Compose Unstyled1.49.6](https://github.com/composablehorizons/compose-unstyled/blob/a08bd29d63bb1165c23a00a19d6fdb5c71467b52/composeunstyled-primitives/src/commonMain/kotlin/ModalBottomSheet.kt#L307-L310), cuyo manejador Android llama BackHandler. No se toca el estado de la app por una API de pruebas ni se omite el menú sin verificarlo.

Antes del único tap en Catálogo, ambos recorridos exigen la pestaña visible y habilitada y ejecutan `waitForAnimationToEnd` con un máximo de 5000 ms. Es una sincronización nativa basada en estabilidad de capturas, no un sleep fijo; Maestro continúa si vence ese plazo. Por ello esta espera por sí sola no acredita interacción ni aceptación. Se conserva obligatoria la aparición de Buscar en el catálogo después del tap, sin reintentos ni pasos opcionales. La diferencia de timing observada entre los dos casos de la revisión v3 justifica comprobar esta sincronización; no demuestra la causa del fallo ni un defecto de la app. Véase [el contrato de Maestro](https://docs.maestro.dev/reference/commands-available/waitforanimationtoend).

La AVD API36 16KB usa RAM guest explícita de `4096M` mediante el input oficial `ram-size`; no se sobrescribe con `-memory` ni opciones QEMU. La ejecución nativa v12 anterior usó el valor por defecto de 2560 MB y registró una terminación por lowmemorykiller, por lo que se corrige el entorno de esta comprobación sin cambiar el APK, heap, API34 ni reintentos. Esta validación en un dispositivo virtual de 4 GB no acredita comportamiento ante escasez de memoria. La sincronización anterior tampoco demuestra que fuese la causa de aquel fallo. Referencias: [input de la acción](https://github.com/ReactiveCircus/android-emulator-runner/blob/main/action.yml) y [recursos del runner público Ubuntu24.04](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

La separación de AVDs permite aceptar cada perfil desde una instalación independiente; no identifica la causa del splash observado en release API34 de v4 ni cambia aquel resultado fallido. Los dos casos por perfil, la espera inicial de 45 segundos y todas las aserciones se conservan. Sólo la AVD16KB recibe 4096M; API34 y el heap no cambian.

Si Maestro falla, antes de limpiar se consulta en memoria el PID del paquete fijo y el crash buffer borrado al comenzar esa fase. El JSON conserva sólo PID enteros validados y códigos JAVA_FATAL/NATIVE_FATAL cuando el mismo bloque identifica expresamente el paquete; no conserva mensajes, stack traces, XML ni logs crudos. Si la consulta o el formato fallan se registra unknown, nunca ausencia de proceso/crash inventada. Esta observación es posterior a la suite: no identifica el caso que causó un evento ni prueba LMK, ausencia de JavaScript o un problema de red. Los errores originales y la limpieza siguen determinando el resultado.
