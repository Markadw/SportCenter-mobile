# Aceptación Android de formularios de correo

El [registro v3](https://github.com/Markadw/SportCenter-mobile/actions/runs/41889146245) aprobó EF01–02. La [verificación v1](https://github.com/Markadw/SportCenter-mobile/actions/runs/41891484613) aprobó EF03–04 y conservó EF05 fallido: el parser rechazó la lectura de UI posterior al envío de recuperación, que quedó incierto para ese runner. [Reset v6](https://github.com/Markadw/SportCenter-mobile/actions/runs/41952937825) aprobó EF06–09: reanudación del código existente, rechazo del incorrecto, cambio de contraseña e inicio y cierre con la nueva contraseña. Su último EF05 volvió a fallar al leer la UI posterior al envío, con operación incierta y limpieza 3/3. La [solicitud independiente v1](https://github.com/Markadw/SportCenter-mobile/actions/runs/41955843077) aprobó EF05 sin incertidumbre y con limpieza 3/3. Son nueve controles distintos, repartidos 2+2+4+1; los dos EF05 fallidos anteriores conservan su estado original. El propietario confirmó separadamente tres recepciones de correo, sin convertirlas en aprobaciones UI. `config/android-email-forms-validation.json` identifica exclusivamente el APK RC6 de la fuente `8831dfad7fd1b0c696d11f50c79442c5499b7cd2`.

La solicitud independiente usó sólo el correo propio, un envío y observación del formulario de recuperación. No hizo registro, reset ni login. Su JSON registró `syntaxDiagnostic` sin lecturas inválidas y un gesto de lectura hasta Actualizar contraseña; no acredita como causa del fallo histórico la actividad del cooldown. Artefacto `13383441300`, 1591 bytes, SHA256 `9e4c204eed0da4df677724aef5efd6cfb454adf5c3f637e9abeda433758a3758`, con únicamente los dos JSON de resultados/procedencia. Mantiene la fuente de aplicación `8831dfa` y automatización `9a79af1`; la integración posterior del tooling no reconstruye ese APK.

El [productor RC6](https://github.com/Markadw/SportCenter-mobile/actions/runs/41860689069/attempts/2), intento 2, aprobó sus ocho trabajos obligatorios, incluidos APK/API34 y rechazo TLS/API30. Los otros tres trabajos quedaron omitidos conforme a su matriz. Su agregado histórico se llama `Resultado de integración`; no se cambia ese nombre al revisar esta ejecución anterior.

La descarga local midió 96156661 bytes; el productor no informa un tamaño del APK independiente, pero su SHA256 coincide. El artifact del intento 2 es `13345177867`, 177731 bytes y SHA256 `758574e02449eb81738e28f460c303ae9555d8774c6a3d21484197eb6920b70e`; se verificaron digest y archivos de procedencia/inspección. No se usa el artifact incompleto del intento 1.

El campo `fingerprint` del recibo es `10e00c0bce8c4ceb0e767388455fad214c4a474db574d7b8c47b703fbb3f9c79`, obtenido de `eas-candidate.json.configFingerprint` y del mensaje EAS `sport-center-candidate-v1:<huella>`. No es el campo `fingerprint.hash` de Expo. La identidad real pasó `verifyProducer`, `verifyArtifact`, `verifyApk` y `verifyBuild`; esto acredita procedencia. La ejecución requiere sus propios resultados por fase y no acredita publicación en Play.

Se usa una cuenta de formularios propia, distinta de la cuenta reservada para carrito/perfil. El correo puede ser un alias del Gmail del propietario. Su teléfono de pruebas debe estar reservado y no ocupado en el backend. El registro deja una cuenta real verificada; no existe una eliminación automática ficticia. La recuperación deja la nueva contraseña como contraseña vigente de esa cuenta. No cambia los secretos originales del repositorio ni las credenciales QA de carrito.

El auxiliar `android-validation.yml` conserva la matriz de tres pipelines principales. Los tags `validation/account-forms-*` activan sólo el job de formularios; el job anterior de cuenta queda excluido de ese prefijo. Ambos usan el entorno ya autorizado `android-private-qa`, con su política existente `validation/account-*`. No se crean aprobadores, entornos ni permisos adicionales.

| Fase | Tag explícito | Controles UI obligatorios |
| --- | --- | --- |
| Registro | `validation/account-forms-register-<caso>` | EF01 crea cuenta con consentimiento y observa Verificar correo; EF02 solicita un reenvío y observa su confirmación. |
| Verificación | `validation/account-forms-verify-<caso>` | EF03 entra mediante Ya tengo un código y observa rechazo del código incorrecto; EF04 exige Cuenta verificada con código correcto; EF05 solicita recuperación y exige el formulario de recuperación. |
| Recuperación | `validation/account-forms-reset-<caso>` | EF06 reanuda el código existente sin otro envío; EF07 rechaza el código incorrecto; EF08 exige Contraseña actualizada; EF09 inicia sesión con la nueva contraseña, cierra sesión y exige Cuenta sin sesión. Después solicita una recuperación nueva y exige su formulario (EF05). |
| Solicitud independiente | `validation/account-forms-request-<caso>` | Sólo EF05: introduce el correo propio, envía una solicitud y observa Código de recuperación y Actualizar contraseña. No registra, verifica, cambia contraseña ni inicia sesión. |

La fase reset sólo solicita ese código nuevo después de consumir el anterior y observar login y logout; no invalida el código usado para la prueba. EF05 exige una observación UI nueva y no modifica los fallos históricos de verificación o reset. Son nueve controles distintos; EF05 aparece en varias fases y no se suma dos veces. No debe repetirse reset v6: la contraseña ya cambió y su código anterior quedó consumido. Una fase request explícita acredita únicamente la solicitud pendiente. El código nuevo se deja expirar tras comprobar la entrega del correo por el propietario.

Request recibe únicamente el correo. El workflow entrega valores vacíos para contraseña, teléfono, OTP y nueva contraseña; el runner rechaza cualquier valor presente en esos cuatro campos. Después del único tap Enviar código espera una sola vez 65 segundos, y luego mantiene la espera UI de 45 segundos y máximo tres lecturas inválidas. El formulario real actualiza su cooldown durante 60 segundos; se separa esa actividad de la observación, sin atribuirle como causa demostrada los fallos anteriores. La pausa no envía peticiones, no consume códigos y no reintenta el POST.

Sólo request añade `syntaxDiagnostic`: número acotado de lecturas inválidas y una categoría sintáctica de una lista fija. La clasificación examina en memoria tamaño, estructura, límites y entidades; no contiene XML, atributos, texto de campos, valores o mensajes de excepción. El parser histórico sigue validando primero y cualquier snapshot rechazado continúa rechazado. Diagnosticarlo no permite aprobarlo. Los JSON históricos conservan su esquema y sus fallos originales.

Cada fase usa un AVD API34 nuevo, el mismo APK identificado por el recibo y el sandbox UID/firewall existente. Maestro está fijado en 2.12.0 con SHA256 verificado. Los valores privados se pasan únicamente mediante `MAESTRO_ACCOUNT_FIELD_VALUE`; no se interpolan en YAML, argumentos ni etiquetas. Antes del envío se comprueba en memoria que el texto introducido coincide; las contraseñas se vuelven a ocultar. XML, flujos y salida Maestro permanecen privados y se eliminan junto con el sandbox.

Las esperas de respuesta admiten hasta tres lecturas de UI inválidas dentro del límite existente de 45 segundos. El parser sigue rechazando XML mal formado, entidades inseguras y DTD; sólo una lectura válida con las etiquetas exigidas confirma el resultado. Se repiten lecturas, nunca el envío. Tras cerrar sesión se abre la ruta fija account y se exige la vista sin sesión y la ausencia del mensaje de cuenta autenticada.

El formulario largo se observa en dos ventanas: primero Código de recuperación; después se desplaza hasta Actualizar contraseña, sin pulsarlo, y exige ese botón. Ambos elementos siguen siendo obligatorios; no se exige que quepan a la vez. `recoveryUi` publica sólo cuatro booleanos fijos de elementos observados y de su última visibilidad. No contiene texto de campos, XML ni capturas. El intento reset v1 agotó la espera del oráculo conjunto sin identificar qué etiqueta faltó; conserva su resultado y no acreditó un cambio de contraseña.

Antes de rellenar se exige la pantalla real: registro con su primer campo habilitado, recuperación con título y Correo habilitado, y login con su descripción y correo habilitado. La espera de 45 segundos incluye el arranque: el montaje de la actividad no demuestra que StartupGate haya expuesto sus descendientes accesibles. No se inicia el scroll inicial UP hasta ver el formulario. Esto elimina una carrera posible; no atribuye retrospectivamente el fallo de reset v2 a una causa que ese informe no distinguía.

`maestroDiagnostic` sólo contiene claves fijas: acción, resultado observado, código de salida acotado, timeout, JUnit leído/válido y enums de clasificación. Los informes históricos conservan scroll/input; el runner nuevo utiliza Maestro sólo para FIELD_BODY de entrada privada y su JUnit real. Los patrones element-not-found/device-offline/timeout se evalúan en memoria; no se publican stdout, stderr, XML, argumentos ni valores. Un timeout no pasa aunque su exitCode sea cero.

Los controles completamente contenidos en el tamaño efectivo de pantalla (`wm size`, incluyendo Override) y en su ScrollView, con un punto válido, no disparan scroll. Si faltan, se exige un `android.widget.ScrollView` propio e inequívoco, bounds válidos dentro de pantalla y un carril lateral fuera del rango X de sus EditText/clickables visibles. Se recortan sus intersecciones; bounds ilegibles, selección ambigua o ausencia de padding impiden cualquier gesto. Form usa padding propio; el runner lo comprueba en la geometría actual, sin asumir que siempre exista.

Reset v5 identificó múltiples ScrollView en el árbol global antes del primer gesto; se conservan el fallo, cinco casos sin completar y limpieza 3/3, sin acreditar reset ni otro correo. El parser privado de formularios ahora conserva la ascendencia en memoria, después de validar todo el XML con el parser histórico intacto. Selecciona el ScrollView más próximo a un control específico; en recuperación prioriza Código de recuperación y Nueva contraseña y exige que sus anclas converjan. Sin ellas sólo sirven Correo o Actualizar contraseña inequívocos. Etiquetas genéricas de otras pantallas no sustituyen un ancla fuerte. Código puede salir del dump: se vuelve a vincular a Nueva contraseña o al botón al bajar y se comprueba el recorrido inverso al volver al campo. No se elige por orden, tamaño de región o coordenadas supuestas.

El carril lateral excluye todos los controles ajenos al subárbol seleccionado. El objetivo se filtra de nuevo al mismo subárbol antes de cada tap o entrada y debe caber completo dentro de la región, además de la pantalla. Las observaciones del campo también se limitan a ese formulario. La ascendencia no se añade a los JSON, no se conserva XML y no se modifica el helper histórico de cuenta. Estos controles locales cubren anidación, pantallas de fondo, anclas que desaparecen al desplazar, ambigüedad y recortes; no sustituyen la siguiente ejecución Android real.

El scroll de lectura usa únicamente `adb input swipe`: dirección correcta, carril de padding, 400 ms, máximo diez gestos y límite de 30 segundos. Relee la UI y recalcula región/carril tras cada gesto; exige el control completo y un punto válido, y vuelve a medir antes del único tap o entrada. No hay centrado adicional ni comandos YAML de scroll. `scrollDiagnostic` publica sólo objetivo enum, dirección, intentos, región/carril encontrados y resultado fijo. Si el control no aparece, no se toca ni escribe y no se repite ningún POST. `exceptionEnum` permanece limitado a categorías públicas conocidas de entrada Maestro, sin mensajes arbitrarios.

El propietario coordina las fases con el conector Gmail existente. Después del registro/reenvío terminado, busca el mensaje correspondiente al alias y propósito exactos y extrae el último código inequívoco. Lo guarda por stdin como `ANDROID_FORMS_CODE` del entorno antes de crear el tag de verificación. Después de EF05 repite la operación con el código de recuperación antes del tag de reset. Los secretos environment se leen cuando comienza el job: actualizar uno no actualiza un job iniciado. Por ello no se deja un runner esperando cambios de secretos ni se exporta OAuth, cookies o sesiones Gmail. No se usan relays, túneles o servicios externos de OTP.

Sólo el último paso recibe los datos de la fase desde el entorno: registro/verificación/reset usan `ANDROID_FORMS_EMAIL`, `ANDROID_FORMS_PASSWORD`, `ANDROID_FORMS_PHONE`, `ANDROID_FORMS_CODE` y `ANDROID_FORMS_NEW_PASSWORD`; request recibe únicamente el correo y los demás vacíos. La contraseña inicial y la nueva deben ser distintas y cumplir el contrato. Ningún secreto de cuenta aparece en prepare, EAS, descarga, KVM o preflight. El token Expo sólo se entrega a build:view; GitHub token sólo a la lectura del productor. Los OTP efímeros se eliminan del entorno después de cerrar el caso. No se elimina ningún secreto anterior ajeno a este flujo.

Los dos JSON publicados contienen fuente, huella, fase, IDs, estados, booleanos, códigos fijos y limpieza. No incluyen correo, teléfono, contraseñas, OTP, IDs de mensajes, capturas, XML ni logs. La entrega Gmail se verifica separadamente por el propietario; el runner declara `not-observed-by-runner`. El rechazo de recuperación acredita la respuesta visible y que no apareció éxito; no inventa un HTTP observado. La pantalla de éxito, el nuevo inicio de sesión y las comprobaciones del servidor se mantienen como condiciones reales del recorrido.

Una fase pasa sólo si todos sus controles y observaciones pasan, no queda una operación incierta y la aplicación, datos locales y sandbox quedan limpiados. Una instalación parcial también se inspecciona y elimina. Ante resultado incierto no se repite automáticamente un registro, reenvío o reset. Se conserva el fallo y se determina el estado de la cuenta antes de preparar una nueva fase explícita. No se publica ni borra un pedido, pago o reseña en este flujo.

La nueva opción de reanudación es una mejora de usuario: permite volver del correo o reabrir la app y usar un código vigente sin solicitar otro. Sólo cambia la etapa del formulario; no persiste códigos ni contraseñas y no llama a `verify-user-token`. El servidor sigue validando y consumiendo el código en `reset-psw`. Su aceptación Android necesita el APK que incluya ese cambio; los resultados RC5 anteriores mantienen su alcance histórico.
